# Обновление: ускорение и стабилизация пакетного пути

Документ описывает, что изменилось в ветке `perf/stability-and-speed`, что
обязательно пересобрать и в каком порядке разворачивать.

## 1. Что изменилось

Формат пакетов на проводе **не менялся**. Версия протокола осталась `1`,
заголовок тот же, Noise тот же (`Noise_IK_25519_ChaChaPoly_SHA256`).

### Скорость

Полный путь пакета (шифрование, обрамление, расшифровка, 1380 байт):
**2361 → 7110 Мбит/с**, то есть 3.0x.

- `snow` теперь собирается с фичей `ring-accelerated`: ассемблерные
  ChaCha20-Poly1305 и SHA-256 вместо чистого Rust. Это дало 2.5x и оказалось
  главным узким местом — шифрование, а не обрамление. Протокол и байты на
  проводе те же, меняется только реализация примитивов.
- `SecureSession` разделён на половины отправки и приёма. Шифрование в Noise не
  требует мутабельного состояния, поэтому направления больше не делят один
  мьютекс: приём стал полностью безблокировочным, отправка не конкурирует ни с
  чем, кроме переподключения.
- Появились `TunnelSender` и `TunnelReceiver` с переиспользуемыми буферами.
  Было 3 аллокации и 3 копии на пакет в каждом направлении, стало 0 и 1.
- Сервер больше не собирает уже разобранную датаграмму обратно в байты только
  для того, чтобы отдать её декодеру. Это стоило полной копии каждого пакета.
- Сессии сервера индексируются и по адресу туннеля, а не только по ID: воркер
  TUN перебирал все сессии линейно на каждый пакет.
- Релизные сборки используют thin LTO и один codegen unit.

### Стабильность

- Сервер подхватывает новый адрес клиента после того, как пакет от него прошёл
  аутентификацию. Раньше смена порта NAT или переход между сетями подвешивали
  сессию до истечения таймаута на стороне клиента.
- Рукопожатие ретрансмитится каждые 700 мс в течение 10 с. Раньше один
  потерянный UDP-пакет проваливал всю попытку подключения.
- Байт-в-байт повторный запрос рукопожатия получает закэшированный ответ, а не
  создаёт вторую сессию. Первое сообщение Noise IK реплеябельно по устройству
  протокола, поэтому дубликат в сети оставлял клиента с ключами, которых он не
  выводил.
- Один пакет, который не удалось закодировать или записать в TUN, больше не
  роняет клиент целиком.
- Временные ошибки ввода-вывода в UDP-цикле и TUN-воркере сервера больше не
  завершают поток молча.
- Таймаут простоя: 30 → 15 с на Linux, 90 → 20 с на Android. Повторные попытки
  с экспоненциальной задержкой 1…16 с вместо фиксированных 10 с.
- Окно защиты от повторов расширено со 128 до 1024.
- MTU туннеля по умолчанию 1420, предупреждение при старте, если настроенное
  значение приведёт к фрагментации, и клампинг TCP MSS в наборе правил.

## 2. Совместимость и порядок развёртывания

> **Сервер обновляется первым.** Это не рекомендация, а требование.

| Сервер | Клиент | Результат |
| --- | --- | --- |
| старый | старый | как раньше |
| **новый** | старый | работает; старые клиенты дополнительно получают роуминг и MSS clamp, но не получают ускорения на своей стороне и ретрансмиссии рукопожатия |
| старый | **новый** | **ломается на плохой связи**: клиент ретрансмитит рукопожатие, старый сервер считает каждую копию новой сессией и оставляет клиента с несовпадающими ключами |
| новый | новый | всё вышеперечисленное |

Проблема в третьей строке проявляется только когда ответ сервера не пришёл за
700 мс — то есть ровно на плохой связи, где ретрансмиссия и нужна. Поэтому:
сначала сервер, потом клиенты.

## 3. Что пересобрать

Всё, что несёт крипто, то есть все три компонента. Пересборка обязательна не
для совместимости, а чтобы получить эффект: ускорение крипто работает на той
стороне, которая шифрует, — сервер ускоряет свою нагрузку, клиент свою.

### 3.1 Сервер

```sh
git pull --ff-only
cargo test --workspace
cargo build --release -p mousevpn-server
sha256sum target/release/mousevpn-server
```

Резервная копия и замена бинарника — по разделу 15 файла [MANUAL.md](../MANUAL.md):

```sh
sudo install -m 0755 /usr/local/bin/mousevpn-server /usr/local/bin/mousevpn-server.backup
sudo install -m 0755 target/release/mousevpn-server /usr/local/bin/mousevpn-server
```

Обновить набор правил (в нём появился клампинг MSS):

```sh
sudo install -m 0640 -o root -g mousevpn deploy/server/mousevpn.nft /etc/mousevpn/mousevpn.nft
sudo systemctl restart mousevpn-network.service
sudo systemctl restart mousevpn-server.service
```

Перед перезапуском отредактируйте в `/etc/mousevpn/mousevpn.nft` значения
`mousevpn_wan` и `mousevpn_net` под свой хост, как и в исходном файле.

### 3.2 Linux-клиент

```sh
cargo build --release -p mousevpn-linux-client
```

Тот же бинарник обслуживает и полный туннель, и режим SOCKS5-прокси.

### 3.3 Android

```sh
cd android
export ANDROID_HOME="$HOME/Android/Sdk"
./gradlew assembleRelease
```

Сборка проверена под обе упаковываемые ABI (`arm64-v8a` и `x86_64`); `ring`
собирается NDK без дополнительных настроек. Проверить только Rust-часть можно
быстрее:

```sh
cargo ndk -t arm64-v8a -t x86_64 build --release -p mousevpn-android-native
```

## 4. Что проверить в конфигурации

### MTU — единственное, что может потребовать правки

Новое значение по умолчанию (1420) применяется **только если поля `mtu` нет** в
`[tun]` секции `/etc/mousevpn/server.toml`. Существующее явное значение
сохраняется как есть.

Проверьте текущее:

```sh
sudo grep -A6 '\[tun\]' /etc/mousevpn/server.toml
```

Накладные расходы на пакет — 65 байт (20 внешний IP, 8 UDP, 20 заголовок
протокола, 1 внутреннее обрамление, 16 тег аутентификации). На обычном пути с
MTU 1500 туннельный MTU не должен превышать 1435; рекомендуемое значение 1420.

Если настроено больше, сервер напишет при старте:

```
MouseVPN warning: tun.mtu = ... produces ... byte datagrams on a 1500 byte path,
which will be fragmented. Use 1420 unless every path is known to carry more.
```

> **Если меняете `mtu`, перезапустите все клиенты.** Сервер передаёт MTU
> клиенту в параметрах сессии, а Linux-клиент завершает работу с
> `SessionParametersChanged`, если параметры изменились при переподключении.

### Остальное менять не нужно

Ключи, адреса, список устройств, `admin.token`, unit-файлы systemd и реестр
`/var/lib/mousevpn/devices.toml` не затронуты.

## 5. Проверка после развёртывания

```sh
systemctl status mousevpn-server.service --no-pager
sudo journalctl -u mousevpn-server.service -n 50 --no-pager
```

В журнале не должно быть предупреждения про MTU. При подключении клиента
появляется привычное `session established for <имя> from <адрес>`. Новая строка
`session for <адрес> moved from <старый> to <новый>` — это штатная работа
роуминга при смене сети или порта NAT.

Измерить пакетный путь на любой машине:

```sh
cargo run --release --example packet_path -p mousevpn-data-plane
```

## 6. Что осталось несделанным

Сознательно не трогалось, потому что относится к безопасности, а не к скорости
и стабильности. Полный разбор — в аудите; кратко:

- в рукопожатии нет метки времени против повтора: перехваченный `HandshakeInit`
  можно переслать и сбросить чужую сессию. Кэш ответов закрывает только
  байт-идентичные дубликаты, но не подделанные заново;
- `HandshakeLimiter` хранит запись на каждый исходный IP и никогда не чистится:
  спуфинг исходных адресов приводит к неограниченному росту памяти;
- ключи сессии не ротируются;
- поле `flags` внешнего заголовка не проверяется и не аутентифицируется;
- `ServerState`, `SessionTable` и `UserRegistry` с лимитами сессий и
  истечением по простою используются только в тестах, а не в демоне.
