# План оптимизации: Android-клиент и сервер

Рабочее задание. Аудит проведён Claude (Opus 5), вопросы по скорости протокола
отдельно проверены через Codex (gpt-5.6-sol); расхождения между двумя разборами
отмечены явно. Linux-клиент в этот аудит не входит — он отлажен отдельно.

Задачи идут в порядке выполнения. Каждая самодостаточна: можно останавливаться
после любой и получать рабочее дерево.

## Главный вывод

Узкое место — **не криптография и не формат пакета**, а один syscall на пакет
и по одному потоку на направление.

Замер на этой машине (`cargo run --release --example packet_path -p mousevpn-data-plane`):

```
       allocating path:    5903 Mbit/s,  1870 ns/packet
   buffer-reusing path:    7069 Mbit/s,  1562 ns/packet
```

7 Гбит/с на пакетах ~1400 байт означает, что шифрование не является пределом ни
для одного реалистичного канала. Оптимизировать AEAD или ужимать заголовок до
перестройки I/O бессмысленно.

## Чего делать НЕ нужно

Эти пункты рассматривались и отклонены — не тратьте на них время.

- **Уплотнять wire-формат.** При MTU 1420 заголовок в 20 байт — это 1,4% от
  полезного пакета, inner kind — 0,07%, весь оверхед протокола 37 байт — 2,6%.
  Сокращение заголовка вдвое даст меньше 1%.
- **Переходить на AES-GCM ради ARMv8 Crypto Extensions.** Cipher suite входит
  в имя Noise-протокола и в handshake hash (`Noise_IK_25519_ChaChaPoly_SHA256`
  против `Noise_IK_25519_AESGCM_SHA256`), то есть это несовместимое изменение
  протокола, требующее переговоров suite, криптографически связанных с
  handshake, иначе появляется downgrade-атака. Порог для возврата к вопросу:
  замеренный выигрыш ≥20–30% на полном пути на реальных телефонах, а не на
  микробенче AEAD.
- **`SO_REUSEPORT`-шардинг сервера.** Хэш reuseport закрепляет один UDP
  4-tuple за одним воркером, поэтому одна сессия не масштабируется, а MouseVPN
  — персональный VPN на несколько устройств. Дополнительно: при NAT-роуминге
  новый 4-tuple уедет на другой воркер, а состояние сессии останется на
  прежнем, что напрямую ломает `adopt_peer` и потребует eBPF-маршрутизации по
  открытому `session_id`. Большая перестройка ради сценария, которого нет.
  Вернуться к вопросу, только если появится много одновременных клиентов.
- **Поднимать MTU с 1420 до 1435.** Около 1% полосы, не стоит риска
  фрагментации.
- **Трогать аллоцирующий API** `TunnelDataPlane::encode_ip` / `decode_ip` /
  `decode` в `crates/data-plane/src/tunnel.rs`. Он используется только тестами
  (`tests/tunnel.rs`, `tests/udp.rs`) и бенчмарком `examples/packet_path.rs`,
  который сравнивает его с zero-alloc путём. В продакшн-пути его нет.

## Задача 1 — Реконнект молча умирает при смене параметров сессии

**Приоритет: критический.** Самый вероятный источник жалобы «VPN отвалился и
не поднимается сам».

Файл: `crates/android-native/src/session.rs:242-248`

```rust
if let Ok((replacement_transport, replacement, parameters)) = result {
    if parameters == self.context.parameters {
        self.install_replacement(replacement_transport, replacement)?;
        self.reconnecting.store(false, Ordering::Relaxed);
        return Ok(());
    }
}
self.next_reconnect = Instant::now() + self.reconnect_backoff;
```

Если сервер после реконнекта выдал другие `SessionParameters` (перезапуск
сервера, изменение пула адресов, адрес занят другим устройством, смена DNS или
MTU в конфиге), успешно установленная сессия **молча выбрасывается**. Цикл
уходит в backoff с потолком 16 секунд и повторяет это бесконечно. При этом
`alive` остаётся `true`, `status()` возвращает `"running"`, Kotlin показывает
подключённое состояние — а трафика нет и не будет, пока пользователь вручную
не переподключится.

Сравнение параметров само по себе правильное: TUN-интерфейс уже создан
Kotlin-слоем с конкретным адресом и MTU, и native-код не может его
переконфигурировать. Неверна реакция.

**Что сделать.** Разделить два исхода реконнекта:

1. Параметры совпали → как сейчас, `install_replacement`.
2. Параметры изменились → завершить сессию: выставить `alive = false`, выйти из
   цикла. Kotlin в `monitor()` увидит статус, отличный от `"running"`, и
   поднимет туннель заново с новым `Builder`. Желательно различать это в
   статусе (например `"parameters-changed"`), чтобы Kotlin мог сразу
   переподключиться, а не показывать «Соединение потеряно».
3. Реконнект не удался вовсе → backoff, как сейчас.

**Критерий приёмки.** Изменение адреса устройства в реестре сервера при
работающем Android-клиенте приводит к автоматическому переподключению с новым
адресом в течение нескольких секунд, без действий пользователя.

## Задача 2 — Исходящий поток Android спит вместо ожидания на дескрипторе

**Приоритет: критический для latency и батареи.**

Файл: `crates/android-native/src/session.rs:83-84`, `:289-326`

`spawn()` переводит TUN в `O_NONBLOCK`:

```rust
fcntl(&tun, FcntlArg::F_SETFL(OFlag::O_NONBLOCK)).context("failed to configure TUN")?;
```

после чего `send_outgoing` крутит `read()` → `WouldBlock` → `thread::sleep(5ms)`
(строка 323). Следствия:

- пакет, пришедший сразу после `WouldBlock`, ждёт 0–5 мс: средняя добавка
  ≈2,5 мс, p99 ≈5 мс. Бьёт по DNS, TLS-handshake, играм — по всему, что
  чувствительно к RTT;
- 200 пробуждений потока в секунду при нулевом трафике: расход батареи и помеха
  deep idle, из-за чего Android агрессивнее душит процесс.

Отдельно: Kotlin выставляет `setBlocking(true)` на `Builder`
(`android/app/src/main/java/dev/mousevpn/app/MouseVpnService.kt:68`), а
native-код перебивает это своим `fcntl`.

**Что сделать.** Заменить sleep-poll на `ppoll`/`epoll` по дескриптору TUN с
таймаутом порядка 250 мс. В набор дескрипторов **обязательно** добавить
`eventfd` (или pipe) для сигналов остановки и реконнекта — иначе поток станет
плохо прерываемым, и `stop()` начнёт ждать до полного таймаута.

Заодно убрать busy-wait на реконнекте: цикл
`while reconnecting { sleep(10ms) }` (строки 290-292) заменить на ожидание того
же eventfd.

`O_NONBLOCK` при этом сохраняется — он нужен, чтобы после пробуждения вычитать
всю очередь без блокировки.

**Критерий приёмки.** При простое туннеля поток просыпается ~4 раза в секунду,
а не 200. RTT до сервера при нулевом фоновом трафике падает примерно на 2–3 мс.

## Задача 3 — Rate limiter сервера растёт в памяти без ограничений

**Приоритет: высокий.** Единственный неограниченный рост в горячем пути.

Файл: `crates/server/src/rate_limit.rs:13`, `:32`

```rust
clients: HashMap<IpAddr, Counter>,
...
let counter = self.clients.entry(address).or_insert(Counter { ... });
```

Запись создаётся для каждого source IP, приславшего `HandshakeInit`, и никогда
не удаляется. До лимитера пакет проходит только фильтр
`looks_like_protocol_datagram` (`crates/data-plane/src/tunnel.rs:313`), то есть
проверку одного байта версии. UDP-флуд со спуфнутыми source-адресами растит
карту неограниченно — примерно 50–70 байт на адрес.

**Что сделать.** Вычищать протухшие записи. Достаточно амортизированной
уборки: при вставке раз в N операций (или раз в `window`) пройтись по карте и
удалить всё, у чего `now - started >= window`. Дополнительно — жёсткий потолок
размера с вытеснением, чтобы поведение было предсказуемым и под всплеском.

**Критерий приёмки.** Тест: подать 100 000 уникальных адресов, продвинуть
время за пределы окна, подать ещё один адрес — размер карты вернулся к
единицам, а не к 100 001. Существующий тест
`limits_and_resets_each_source` должен продолжать проходить.

### Задача 3b — Лимит душит легитимные ретрансмиты

Файл: `crates/server/src/daemon.rs:112`

```rust
let mut handshake_limiter = HandshakeLimiter::new(10, Duration::from_secs(60));
```

Клиент за одну попытку подключения шлёт до 15 датаграмм: `TIMEOUT = 10s` при
`RETRANSMIT = 700ms` (`crates/android-native/src/handshake.rs:16-21`). Лимит —
10 за 60 секунд на IP. То есть одна неудачная попытка выбирает весь бюджет, и
следующая в пределах минуты будет частично отброшена. За общим NAT (несколько
устройств одного пользователя) это срабатывает ещё легче.

**Что сделать.** Поднять лимит так, чтобы он покрывал минимум 2–3 полные
попытки подключения (ориентир: 40–50 за 60 секунд), сохранив защиту от флуда.
Кэш повторов в `handle_handshake` (`daemon.rs:259-264`) уже делает повторные
запросы дешёвыми, так что запас безопасен.

## Задача 4 — Android дёргает Keystore и грузит иконки на main thread

**Приоритет: высокий.** ANR-класс.

### 4a. `ProfileStore.selected()` на каждое обновление статуса

Файлы: `android/app/src/main/java/dev/mousevpn/app/MainActivity.kt:256`,
`android/app/src/main/java/dev/mousevpn/app/ProfileStore.kt:34-37`

Цепочка `applyStatus()` → `updatePowerEnabled()` → `store.selected()` →
`list()` → `decrypt()` выполняет `KeyStore.getInstance("AndroidKeyStore")` +
`load(null)` + `getKey` + AES-GCM. Это Binder-вызовы в демон keystore2, то есть
миллисекунды, а не микросекунды. Происходит на **каждый** broadcast статуса, а
также в `refreshProfile`, `requestConnection`, `showProfileChooser`,
`showProfileMenu`.

**Что сделать.** Кэшировать расшифрованный список профилей в `ProfileStore` и
инвалидировать кэш в `save`/`delete`/`select`. `SecretKey` из Keystore тоже
получать один раз, а не на каждый вызов `key()`.

### 4b. `AppListActivity` грузит все приложения и иконки в `onCreate`

Файлы: `android/app/src/main/java/dev/mousevpn/app/AppListActivity.kt:45`,
`:103-125`

`loadApps()` вызывается синхронно из `onCreate` и для каждого приложения
дёргает `getApplicationLabel` и `getApplicationIcon`. На устройстве со 150
приложениями это 1–3 секунды заморозки UI, плюс все `Drawable` держатся в
памяти одновременно.

**Что сделать.** Список грузить в фоне с плейсхолдером на время загрузки.
Иконки не грузить в `InstalledApp` вообще — доставать лениво в `getView` с
LRU-кэшем, ограниченным по размеру. Метки можно оставить в модели, они дешёвые.

**Критерий приёмки.** Открытие экрана выбора приложений не блокирует UI-поток
дольше кадра; в StrictMode нет нарушений на main thread.

## Задача 5 — Роуминг вместо полного handshake при смене сети

**Приоритет: средний.** Крупное улучшение ощущаемой стабильности.

Файлы: `android/app/src/main/java/dev/mousevpn/app/MouseVpnService.kt:20-24`,
`crates/android-native/src/session.rs:235-253`,
`crates/server/src/daemon.rs:49-67`

Сервер **уже умеет роуминг**: `adopt_peer` переносит сессию на новый адрес и
порт после того, как пакет прошёл аутентификацию. Клиент этим не пользуется —
любое `onAvailable`/`onLost` приводит к полному Noise IK handshake с новым
сокетом и новым `session_id`, то есть к простою от 1 до 10 секунд.

**Что сделать.** При запросе реконнекта сначала пробовать миграцию:

1. Создать новый UDP-сокет и вызвать `protect()` (это необходимо, чтобы Android
   привязал сокет к новой сети).
2. Перенести на него существующие `TunnelSender`/`TunnelReceiver` **без**
   пересоздания криптосессии.
3. Отправить keepalive. Сервер аутентифицирует его и сам подхватит новый peer.
4. Если ответа нет после N попыток (ориентир: 3 попытки за ~1,5 с) — падать в
   текущий полный handshake.

Sequence и replay-окно при миграции сохраняются, и это правильно: nonce
остаются уникальными, повторов не появляется.

Добавить дебаунс на `signalNetworkChange` (порядка 300–500 мс): cellular
handover генерирует пачки событий, и каждое сейчас запускает реконнект.

**Критерий приёмки.** Переключение Wi-Fi → LTE при активной загрузке
восстанавливает трафик за время порядка сотен миллисекунд, без нового
handshake в логах сервера.

## Задача 6 — Метрики

**Приоритет: средний, но выполнить до задачи 7.** Без них оптимизация вслепую.

Сейчас нет ни счётчиков пакетов, ни дропов, ни времени handshake, ни RTT.

**Что сделать.**

- Android: считать пакеты и байты в обе стороны, дропы в
  `write_packet_nonblocking` (`crates/android-native/src/session.rs:378` —
  сейчас переполнение очереди TUN проглатывается молча), число реконнектов и
  их длительность. Отдавать через `status()`.
- Сервер: то же по сессиям, плюс проверять **фактические** `SO_RCVBUF`/
  `SO_SNDBUF` после установки (`crates/server/src/daemon.rs:190-194` просит
  8 МиБ, но ядро режет по `net.core.rmem_max`), и наблюдать `SO_RXQ_OVFL` и
  UDP drops из `/proc/net/udp`.
- Заглушить `eprintln!` в `adopt_peer` (`daemon.rs:60`): при флаппинге сети
  клиента это лог-шторм под глобальным локом stderr. Оставить, но с троттлингом.

## Задача 7 — Батчинг syscall'ов

**Приоритет: средний.** Основной запас по пропускной способности.

Сейчас один пакет = два syscall в каждую сторону. На 100 Мбит/с при MTU 1420
это ~9 000 пакетов/с, то есть ~36 000 syscall/с. На мобильном CPU это дороже
самой криптографии.

**Что сделать.** `recvmmsg`/`sendmmsg` с батчем 32 на UDP-сокете, на сервере и
на Android. Ожидаемый выигрыш: +20–70% pps, до ~2× на мелких пакетах.

Важное ограничение, отмеченное при разборе: после батч-приёма по UDP остаётся
отдельный `tun.send()` на каждый пакет, поэтому эффект будет меньше
теоретического, пока TUN не вычитывается/записывается пачками тоже. На Android
после задачи 2 это естественно ложится на цикл `ppoll` → вычитать всё
доступное → отправить одним `sendmmsg`.

Заодно: в `handle_client_data` (`crates/server/src/daemon.rs:326-339`)
`session.inbound.lock()` удерживается через `tun.send()` — освободить сразу
после расшифровки и обновления replay-окна. Сейчас безвредно (один поток), но
станет узким местом при любом параллелизме.

## Задача 8 — Мелочи, которые можно взять попутно

- **Двойной парсинг IPv4 на приёме сервера.** `Ipv4Packet::parse` вызывается в
  `TunnelReceiver::decode_into` (`crates/data-plane/src/tunnel.rs:291`), а затем
  повторно в `handle_client_data` (`crates/server/src/daemon.rs:332`) ради
  проверки source. Ожидаемый выигрыш 2–5%.
- **Буферы на Android.** Три буфера по 65 535 байт
  (`crates/android-native/src/session.rs:165`, `:286`, `:288`) при MTU 1420.
  Примерно 256 КБ резидентной памяти впустую; на Android память влияет на
  приоритет при отстреле процессов.
- **`NativeBridge.stop()` вызывается с main thread.**
  `android/app/src/main/java/dev/mousevpn/app/MouseVpnService.kt:199` и `:230`;
  `stop()` делает `worker.join()` (`crates/android-native/src/registry.rs:99`).
  Если worker в середине handshake, main thread блокируется до ~700 мс. Унести
  в executor. После задачи 2 (eventfd) задержка станет пренебрежимой, но вызов
  с main thread всё равно стоит убрать.
- **`monitor()` опрашивает состояние раз в секунду**
  (`android/app/src/main/java/dev/mousevpn/app/MouseVpnService.kt:176-193`),
  каждый раз через JNI и глобальный мьютекс реестра
  (`crates/android-native/src/registry.rs:82`). Либо увеличить интервал до 3–5
  секунд, либо сделать колбэк из Rust при смене состояния.
- **`isMinifyEnabled = false`** в release-сборке
  (`android/app/build.gradle.kts`). Включить R8.
- **Собираются только `arm64-v8a` и `x86_64`** (`android/app/build.gradle.kts`),
  при `minSdk = 26`. Устройства `armeabi-v7a` не смогут установить APK. Либо
  добавить ABI, либо осознанно поднять требования и записать это.
- **`crates/android-native/Cargo.toml`** объявляет только `[lints.clippy]` и не
  наследует `[workspace.lints]`, поэтому на него не распространяется
  `unsafe_code = "forbid"`. В крейте действительно есть `unsafe`
  (`File::from_raw_fd`, `session.rs:83`) — он обоснован и прокомментирован, но
  расхождение стоит сделать явным, а не случайным.

## Отдельно: безопасность, не скорость

Внешний заголовок **не аутентифицирован**. `encrypt_into` в
`crates/crypto/src/session.rs:152-165` вызывает `write_message(sequence,
plaintext, output)`; snow не принимает AAD, поэтому `version`, `kind`, `flags`
и `session_id` подменяемы. Взлома это не даёт — подмена приводит к провалу
расшифровки или промаху по сессии, — но свойство сейчас неявное.

Оба разбора сошлись: **если когда-нибудь менять wire-формат, то ради AAD над
открытым заголовком, а не ради экономии байтов.** Пока формат не меняется —
зафиксировать это свойство в `docs/THREAT_MODEL.md` явно.

Не выполнять в рамках этого плана: это изменение протокола, требующее
отдельного решения.
