# Проверка скорости и стабильности MouseVPN

Этот сценарий нужен перед выпуском новой серверной или клиентской сборки. Он
измеряет реальный путь TUN ↔ UDP, который не покрывает микробенчмарк
`packet_path`.

## Подготовка

Используйте отдельное тестовое устройство и не запускайте UDP-нагрузку на
пользовательском сервере в часы активности. На VPN-сервере установите
`iperf3`, затем запустите его на адресе туннеля:

```sh
iperf3 -s -B 10.77.0.1
```

Если адрес сервера в `[tun]` отличается, подставьте его вместо `10.77.0.1`.
Запишите перед тестом:

- версию и SHA-256 серверного бинарника;
- версию клиента и тип устройства;
- Wi-Fi, Ethernet или мобильную сеть;
- MTU туннеля;
- фактические размеры UDP-буферов из журнала сервера.

## Пропускная способность

После подключения MouseVPN выполните на клиенте по три запуска каждого теста:

```sh
# Клиент → сервер
iperf3 -c 10.77.0.1 -P 4 -t 60 -O 5

# Сервер → клиент
iperf3 -c 10.77.0.1 -P 4 -t 60 -O 5 -R

# Один поток: выявляет проблемы с окном TCP и потерями
iperf3 -c 10.77.0.1 -P 1 -t 60 -O 5
iperf3 -c 10.77.0.1 -P 1 -t 60 -O 5 -R
```

Сохраните JSON хотя бы для итоговых запусков:

```sh
iperf3 -c 10.77.0.1 -P 4 -t 60 -O 5 -J > mousevpn-upload.json
iperf3 -c 10.77.0.1 -P 4 -t 60 -O 5 -R -J > mousevpn-download.json
```

Сравнивайте медиану трёх запусков, а не один лучший результат. Регрессией
считать падение более чем на 10% при сопоставимой сети и загрузке сервера.

## PPS и перегрузка очередей

Только на стенде постепенно увеличивайте UDP-нагрузку. Не начинайте сразу с
максимальной полосы:

```sh
iperf3 -c 10.77.0.1 -u -b 20M -l 256 -t 30
iperf3 -c 10.77.0.1 -u -b 50M -l 256 -t 30
iperf3 -c 10.77.0.1 -u -b 100M -l 256 -t 30
```

После каждого запуска проверьте:

```sh
systemctl status mousevpn-server.service --no-pager
journalctl -u mousevpn-server.service --since '-5 min' --no-pager
ss -u -s
nstat -az | grep -E 'Udp(InErrors|RcvbufErrors|SndbufErrors)'
```

Ожидаемое поведение при заполнении очереди: растёт счётчик drops, но сервер и
туннель не завершаются. Неприемлемы `TUN worker stopped`, циклические рестарты
и состояние клиента «подключено» без передачи данных.

## Android: переключение сети

Во время TCP-загрузки выполните каждый сценарий не менее пяти раз:

1. Wi-Fi → LTE.
2. LTE → Wi-Fi.
3. Выключить текущую сеть на 10 секунд и вернуть её.
4. Выключить сеть на 30 секунд и вернуть её.
5. Перезапустить сервер во время загрузки.

Фиксируйте время от последнего успешного пакета до восстановления трафика.
Быстрая миграция обычно должна занимать до нескольких секунд; после полного
обрыва допустим reconnect с backoff 1…16 секунд. Ручное отключение VPN не должно
запускать автоматический reconnect.

После серии экспортируйте JSON на экране «Диагностика». Проверьте соответствие
`networkChanges`, `sessionTimeouts`, `peerUnreachable`, `reconnects` и
`reconnectFailures` выполненным сценариям.

## Длительный тест

Оставьте Android-клиент подключённым на 8–24 часа с обычным трафиком. В конце
проверьте:

- VPN не находится в ложном состоянии «Подключено»;
- число reconnect объясняется реальными сменами сети;
- `tunDrops` и `udpSendDrops` не растут без нагрузки;
- приложение не показывает заметного дополнительного расхода батареи;
- диагностическая база содержит не более 100 сессий и не отправляет данные
  автоматически.

## Локальные проверки перед сборкой

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo run --release --example packet_path -p mousevpn-data-plane

cd android
ANDROID_HOME="$HOME/Android/Sdk" ./gradlew :app:lintDebug
```

Windows-клиент обязательно проверять на настоящей Windows-машине: Linux CI
собирает только платформенную заглушку и не проверяет поведение Wintun.
