# Совместимое обновление протокола: скорость и устойчивость

Изменены общие библиотеки `mousevpn-morph` и `mousevpn-crypto`, используемые
сервером, Linux- и Android-клиентами. Рабочие VPN-серверы не обновлялись.
На рабочей станции установлен Linux-пакет `mousevpn 0.1.10-1`; запущенный
VPN-клиент не перезапускался, поэтому действующая сессия не прерывалась.

## Поведение

- MouseMorph получает nonce, выбор длины и содержимое padding одним запросом
  к системному CSPRNG вместо двух или трёх. Они занимают непересекающиеся
  участки случайного буфера. Nonce остаётся случайным 96-битным значением для
  каждой передачи, padding — случайным, его распределение и пределы сохранены.
- При проверке маршрутного тега первым проверяется текущий временной интервал.
  Для обычного пакета нужен один HMAC вместо двух. Предыдущий и следующий
  интервалы по-прежнему допустимы; направление и AEAD проверяются как раньше.
- Окно защиты от повторов расширено с 1024 до 8192 номеров. Например, пакет
  с номером 1 теперь принимается после пакета 4096, если раньше не был принят
  и прошёл аутентификацию. Дубликаты и пакеты вне окна отбрасываются.
- Вместо массива номеров используется кольцевая битовая карта: 1032 байта
  вместо 8192 байт на принимающую криптосессию, без учёта метаданных объекта
  и аллокатора. Дополнительное 64-битное слово сохраняет старейший частичный
  блок при продвижении окна. Подход описан в
  [RFC 6479](https://www.rfc-editor.org/rfc/rfc6479.html); здесь окно содержит
  ровно 8192 номера, а кольцо — 129 слов. Обновление выполняется только после
  успешной аутентификации.

Это увеличивает допустимую глубину перестановки пакетов. Реальная частота
разрывов на мобильной сети этим тестом не измерена: потери из-за сети, MTU,
переполнения UDP/TUN и переключений интерфейсов требуют отдельных наблюдений.

## Совместимость

Сохранены Noise IK, ключи, формат legacy, MouseMorph format version 2,
размеры заголовков, теги, padding, MTU, настройки профилей и handshake.
Новый режим в интерфейсе и переключение протокола не требуются. Механизмы
обхода блокировок не менялись. Изменение версии wire-формата не требуется.

Старый клиент может работать с обновлённым сервером, а новый — со старым.
Расширенное окно действует только на обновлённой принимающей стороне:
обновление сервера улучшает приём от клиентов; обновление клиента — приём
от сервера. Оно не заставляет отправителя переставлять пакеты.

Для регрессии сохранена независимая копия прежнего Morph-кодека из коммита
`ffb264a49dd9643ec44432c617b612aedfd0cf96` в
`crates/morph/tests/support/v2_reference.rs`. Тесты проверяют обмен между
старым и новым кодом в обе стороны, все три профиля, оба направления и каждую
длину полезной нагрузки 0–1430 байт. Проверены cover frames, предел размера
и отказ при изменении любого байта старого кадра.

## Локальные замеры

Linux x86-64, системный Rust 1.98.1, release, thin LTO, один codegen unit.
Базовая версия — указанный выше коммит. Пять запусков каждой версии,
порядок старой/новой чередовался. В таблице медианы времени на одну пару
encode/decode; по 100 000 пакетов каждого размера и 1000 прогревочных
итераций. Профиль Balanced, буферы переиспользуются.

| Внутренняя нагрузка | До, нс | После, нс | Снижение времени |
| ---: | ---: | ---: | ---: |
| 64 байта | 6292 | 5242 | 16,7% |
| 512 байт | 6892 | 5849 | 15,1% |
| 1317 байт | 8171 | 7090 | 13,2% |

Это стоимость внешней оболочки в памяти, а не скорость VPN через интернет.
В примере нет TUN, UDP, JNI и конкуренции потоков; числа нельзя переносить
на Android или считать обещанием такого же прироста пропускной способности.

Проверка существующим `packet_path` для основного криптографического пути:
медиана buffer-reusing — 1572 нс до и 1576 нс после (+0,25%, в пределах
наблюдаемого разброса). Увеличение окна не дало заметной регрессии в этом
сценарии; отдельного выигрыша скорости от него не заявляем.

Повторить замеры:

```sh
cargo run --release -p mousevpn-morph --example morph_path
cargo run --release -p mousevpn-data-plane --example packet_path
```

## Проверки и границы

Прошли 68 тестов выбранных компонентов, без пропусков и ошибок:

```sh
cargo test -p mousevpn-server -p mousevpn-linux-client \
  -p mousevpn-android-native -p mousevpn-client-wire \
  -p mousevpn-data-plane -p mousevpn-protocol \
  -p mousevpn-crypto -p mousevpn-morph

cargo clippy -p mousevpn-server -p mousevpn-linux-client \
  -p mousevpn-android-native -p mousevpn-client-wire \
  -p mousevpn-data-plane -p mousevpn-protocol \
  -p mousevpn-crypto -p mousevpn-morph --all-targets -- -D warnings

cargo fmt -p mousevpn-morph -p mousevpn-crypto --check
```

Включены тесты реальных локальных UDP-сокетов, старого/нового кодеков,
полностью обратного порядка 8192 пакетов, границ битовых блоков, больших
скачков номеров, 100 000 сравнений с независимой моделью множества и
проверка, что неаутентифицированный скачок не стирает историю повторов.

Общий `cargo fmt --all --check` показывает существующие расхождения
форматирования в Windows-коде; эти файлы в рамках обновления не менялись.
Android native проверен на Linux-хосте и собран NDK 27 для `arm64-v8a` и
`x86_64` с Rust 1.97.1. На рабочей станции установлены JDK 17, Android
command-line tools 19.0, API 36, build-tools 35.0.0 и cargo-ndk 4.1.2.
Работа на Android-устройстве пока не проверена.

Следующая проверка перед распространением — сценарии из
`PERFORMANCE_TESTING.md`: Linux и Android, загрузка в обе стороны, Wi-Fi/LTE,
смена сети и старые клиенты на обновлённом тестовом сервере. Для сравнения
нужны одинаковые сеть, профиль и MTU, счётчики потерь/переподключений и RTT.
