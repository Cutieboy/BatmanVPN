# План работ: Windows- и Linux-клиенты

Продолжение [OPTIMIZATION_TASKS.md](OPTIMIZATION_TASKS.md), который покрывал
Android и сервер. Аудит проведён Claude (Opus 5) после того, как задачи по
Android и серверу были выполнены; Windows- и Linux-клиенты тогда не менялись и
частично отстали от Android по стабильности.

Задачи идут в порядке выполнения. Каждая самодостаточна.

## Прежде чем начинать

**В ветке есть незакоммиченные регрессии из предыдущего этапа.** Они не входят
в этот файл, но одна из них блокирует задачу L2:

1. `UdpTransport::send_batch` при частичной отправке возвращает
   `io::ErrorKind::WriteZero`, а вызывающий код в
   `crates/android-native/src/session.rs` считает эту ошибку фатальной и рвёт
   туннель. `ENOBUFS` в середине батча — штатная ситуация под нагрузкой.
2. TUN-воркер сервера делает `truncate(length)` и затем
   `resize(DATAGRAM_BUFFER_LEN, 0)` на каждый пакет — 1168 нс замеренного
   memset на пакет при полезной работе в ~780 нс.
3. Rate limiter вытесняет произвольную запись при переполнении, что позволяет
   атакующему сбросить собственный счётчик попыток.

Пункт 1 нужно закрыть **до** задачи L2, иначе Linux-клиент унаследует тот же
обрыв туннеля. Контракт должен стать таким: `send_batch` возвращает число
фактически отправленных датаграмм, а не ошибку, и решение о судьбе хвоста
принимает вызывающий код.

## Чего делать НЕ нужно

- **Менять wire-формат или Noise suite.** Это отдельное решение с
  версионированием протокола, вне рамок этого файла. Текущие изменения обязаны
  оставаться совместимыми со старыми клиентами и с уже развёрнутым сервером.
- **Вводить `SO_REUSEPORT`-шардинг** — обоснование в
  [OPTIMIZATION_TASKS.md](OPTIMIZATION_TASKS.md).
- **Трогать `Liveness`.** Значения `KEEPALIVE_INTERVAL = 10s` и
  `SESSION_TIMEOUT = 20s` совпадают в Windows- и Linux-клиентах и с Android;
  расхождение здесь сломает предсказуемость поведения.

# Windows

## W1 — Смена параметров сессии навсегда ломает клиент

**Приоритет: критический.**

Ошибка есть в двух местах, и чинить нужно оба.

`crates/windows-client/src/packet_loop.rs:196`

```rust
if parameters != self.parameters {
    return Err(ClientError::Platform(
        "server changed tunnel parameters during reconnect".to_owned(),
    ));
}
```

`crates/windows-client/src/runtime.rs:123`

```rust
if next_parameters != parameters {
    return Err(ClientError::Platform(
        "server changed tunnel parameters during runtime restart".to_owned(),
    ));
}
```

`parameters` связывается один раз в `runtime.rs:53` и никогда не
переприсваивается. Когда сервер выдаёт другие `SessionParameters` (перезапуск
сервера, изменение пула адресов, адрес занят другим устройством, смена DNS или
MTU в конфиге), происходит следующее: пакетный цикл возвращает фатальную
ошибку, внешний restart-цикл `runtime.rs:111-154` её ловит, переподключается,
снова видит несовпадение и снова падает — **бесконечно, с backoff до 16 секунд
и полным Noise-handshake на каждой итерации**. Клиент никогда не восстановится.

Это тот же класс дефекта, что был на Android (задача 1 предыдущего файла), но
с другим механизмом: Android висел молча, Windows крутится в цикле и жжёт
handshake каждые 16 секунд.

**Что сделать.** Обрабатывать смену параметров как штатное событие, а не как
ошибку:

1. Сделать `parameters` в `run_with_stop` изменяемой.
2. При получении новых параметров переустановить сетевую конфигурацию:
   `NetworkGuard` создаётся в `runtime.rs:73` с параметрами и владеет адресом,
   маршрутами и DNS. Понадобится либо метод переустановки на `NetworkGuard`,
   либо аккуратный `drop` старого guard'а и установка нового — во втором случае
   обязательно проверить, что kill switch не снимается в промежутке.
3. Обновить MTU адаптера (`adapter.set_mtu`, уже вызывается в `runtime.rs:130`)
   и перезапустить сессию Wintun.
4. Сохранить новые параметры и продолжить работу.

Ориентир для реализации — `apply_session_parameters` в
`crates/linux-client/src/packet_loop.rs:208-237`. Там это уже сделано
правильно, включая откат при неудаче.

**Критерий приёмки.** Изменение адреса устройства в реестре сервера при
работающем Windows-клиенте приводит к автоматическому переходу на новый адрес
без вмешательства пользователя и без снятия kill switch. В логе появляется
`MOUSEVPN_STATE=parameters_updated`, а не бесконечная череда
`MOUSEVPN_RUNTIME_WARNING`.

## W2 — Во время реконнекта пакеты вычитываются и выбрасываются

**Приоритет: критический для ощущаемой стабильности.**

`crates/windows-client/src/packet_loop.rs:268-275`

```rust
let packet = session.receive_blocking().map_err(...)?;
if reconnecting.load(Ordering::Acquire)
    || packet.bytes().first().map(|byte| byte >> 4) != Some(4)
{
    continue;
}
```

Поток извлекает пакет из кольца Wintun и **молча его уничтожает**, если идёт
реконнект. Реконнект длится от секунды до полного таймаута handshake, и всё это
время каждый исходящий пакет пропадает. Для TCP это потеря всего окна в полёте:
после восстановления соединения потребуется повторный медленный старт, и
пользователь видит не «пауза на 2 секунды», а «интернет умер на 15 секунд».

Android решает это иначе и правильно: во время реконнекта он **перестаёт
читать** TUN, очередь наполняется, приложения получают естественный
backpressure, и после восстановления данные уходят без потерь.

**Что сделать.** Не вычитывать кольцо, пока `reconnecting` установлен.
`session.receive_blocking()` блокирует поток без возможности отмены, поэтому
нужен один из вариантов:

- перейти на неблокирующий `session.try_receive()` в паре с
  `session.get_read_wait_event()` и ждать одновременно на этом событии и на
  событии отмены (аналог `eventfd`, который использован в Android);
- либо, как минимум, проверять `reconnecting` **до** чтения и ждать на событии
  отмены, а не осушать кольцо.

Второй вариант проще и уже закрывает основную проблему.

Отдельно: отбрасывание IPv6-пакетов (`byte >> 4 != 4`) должно остаться, но его
следует отделить от проверки `reconnecting` — сейчас это одно условие, и
намерения смешаны.

**Критерий приёмки.** Загрузка файла по TCP переживает принудительный
реконнект без обрыва соединения; счётчик отброшенных пакетов
(`note_packet_drop`) во время реконнекта не растёт.

## W3 — Нет реакции на смену сети и выход из сна

**Приоритет: высокий.**

Поиск по `crates/windows-client/` и `windows-gui/` не находит ни
`WM_POWERBROADCAST`, ни `PBT_APMRESUMEAUTOMATIC`, ни
`NotifyIpInterfaceChange`, ни `NotifyUnicastIpAddressChange`, ни
`NotifyRouteChange2`. Единственный механизм обнаружения — таймаут живости в
`Liveness`, то есть **до 20 секунд** простоя после переключения Wi-Fi ↔
Ethernet или выхода ноутбука из сна.

Android узнаёт об этом мгновенно через `ConnectivityManager.NetworkCallback` и
переподключается за сотни миллисекунд.

**Что сделать.**

1. Подписаться на `NotifyUnicastIpAddressChange` (или
   `NotifyIpInterfaceChange`) для событий смены адресов физических интерфейсов.
   Фильтровать события самого адаптера MouseVPN, иначе установка туннеля будет
   сама себя запускать по кругу.
2. Подписаться на уведомления питания: `PowerRegisterSuspendResumeNotification`
   для служб, либо `WM_POWERBROADCAST` при наличии окна. Событие
   `PBT_APMRESUMEAUTOMATIC` должно приводить к тем же действиям, что и смена
   сети.
3. Оба источника выставляют уже существующий `reconnect_requested`, который
   пакетный цикл читает на `packet_loop.rs:136`. Механизм реакции менять не
   нужно — нужен только источник события.
4. Добавить дебаунс порядка 400 мс, как на Android
   (`NETWORK_CHANGE_DEBOUNCE_MS`): смена сети генерирует пачки уведомлений.

**Критерий приёмки.** Переключение Wi-Fi → Ethernet и выход из сна
восстанавливают туннель заметно быстрее 20 секунд, без ожидания таймаута
живости.

## W4 — Батчинг отсутствует полностью

**Приоритет: средний.** Выполнять после W1–W3.

Сейчас один пакет = один `session.receive_blocking()` плюс один
`transport.send()`. Новый `UdpTransport::send_batch` для Windows недоступен: он
объявлен под `#[cfg(any(target_os = "linux", target_os = "android"))]` в
`crates/transport/src/udp.rs`.

**Что сделать.**

1. Осушать кольцо Wintun пачками: после пробуждения по
   `get_read_wait_event()` вычитывать `try_receive()` до пустоты или до 32
   пакетов, затем шифровать их одной группой.
2. Для отправки на Windows нет аналога `sendmmsg`. Реалистичные варианты:
   несколько `WSASendMsg` через overlapped I/O, либо просто последовательные
   `send()` — экономия придётся в основном на стороне Wintun, а не UDP.
   Замерить, прежде чем усложнять.
3. Если добавляется Windows-ветка batch-API в `transport`, она должна
   следовать тому же контракту, что и исправленный `send_batch`: возвращать
   число отправленных датаграмм, а не ошибку.

**Критерий приёмки.** Измеренный pps в направлении клиент → сервер вырос; при
этом ни одна из проверок W1–W3 не сломалась.

## W5 — Лишнее копирование на приёме

**Приоритет: низкий.**

`crates/windows-client/src/packet_loop.rs:330`

```rust
destination.bytes_mut().copy_from_slice(packet);
```

Расшифрованный пакет копируется из буфера `plaintext` в слот кольца Wintun.
Копирования можно избежать: длина открытого текста известна до расшифровки
(длина шифртекста минус тег и минус байт inner kind), так что можно выделить
слот заранее и расшифровывать прямо в него.

Потребует расширения API `TunnelReceiver::decode_into`, который сейчас требует
`&mut Vec<u8>`. Делать только если замер W4 покажет, что копирование заметно.

## W6 — Остановка ждёт следующего пакета

**Приоритет: низкий.**

`session.receive_blocking()` в `packet_loop.rs:268` блокируется без таймаута,
поэтому `stopping` проверяется только после прихода очередного пакета. На тихом
туннеле остановка клиента подвисает. Решается тем же событием отмены, что и W2
— имеет смысл делать эти две задачи вместе.

# Linux

Логика реконнекта здесь самая зрелая из трёх клиентов: `apply_session_parameters`
корректно переконфигурирует TUN и DNS с откатом при ошибке, а generation-счётчик
защищает от того, чтобы запоздавшая ошибка старого сокета уронила новую сессию.
Оптимизации прошлого этапа сюда просто не дошли.

## L1 — Нет быстрого роуминга, каждый реконнект это полный handshake

**Приоритет: высокий.**

`crates/linux-client/src/packet_loop.rs:185-206`

```rust
fn establish_replacement(&mut self) -> Result<(), ClientError> {
    let (replacement_transport, replacement, parameters) = connect(self.config)?;
```

`connect` всегда выполняет полный Noise IK handshake. Между тем сервер умеет
роуминг: `adopt_peer` в `crates/server/src/daemon.rs:54` переносит сессию на
новый адрес и порт после того, как пакет прошёл аутентификацию. Android этим
уже пользуется и восстанавливается за сотни миллисекунд вместо секунд.

**Что сделать.** Повторить схему `try_migrate` из
`crates/android-native/src/session.rs`:

1. Создать новый UDP-сокет (обязательно новый: старый сохраняет прежний
   source-адрес и закешированный маршрут после suspend — это уже отмечено в
   комментарии на `crates/linux-client/src/outgoing.rs:56`).
2. Перенести на него существующие `TunnelSender`/`TunnelReceiver` **без**
   пересоздания криптосессии.
3. Отправить keepalive, дождаться ответа. Получение ответа доказывает, что
   сервер принял нового peer, потому что `handle_keepalive` отвечает на
   источник пакета и вызывает `adopt_peer` до отправки ответа.
4. Три попытки с таймаутом 500 мс; при неудаче — существующий
   `establish_replacement` без изменений.

Sequence и replay-окно при миграции сохраняются, и это правильно: nonce
остаются уникальными, повторов не появляется.

Обновление маршрута до сервера (`routes.refresh_server_route()` в
`packet_loop.rs:165`) должно выполняться **перед** попыткой миграции, иначе
новый сокет уйдёт по старому маршруту.

**Критерий приёмки.** Переключение сети при активной загрузке восстанавливает
трафик за сотни миллисекунд; в логе сервера при этом появляется строка
`session ... moved from ... to ...`, а не `session established for ...`.

## L2 — Батчинг syscall'ов

**Приоритет: средний.** Требует, чтобы контракт `send_batch` был исправлен
(см. раздел «Прежде чем начинать»).

`crates/linux-client/src/outgoing.rs:45-85` читает по одному пакету
(`tun.receive`) и отправляет по одному (`transport.send`). На приёмной стороне
`packet_loop.rs:108` — то же самое.

**Что сделать.**

1. Исходящее направление: перевести TUN в неблокирующий режим
   (`LinuxTun::set_nonblocking`, метод уже добавлен для сервера в
   `crates/linux-platform/src/tun_device.rs`), ждать на `poll` по fd TUN, после
   пробуждения вычитывать до 32 пакетов и отправлять одним `send_batch`.
2. Входящее направление: `receive_batch` на UDP-сокете, затем расшифровка и
   запись в TUN пачкой.
3. **Не повторять ошибку серверного TUN-воркера**: не делать `truncate` буфера
   с последующим `resize` обратно до полного размера. Хранить длины отдельным
   массивом. На буферах в 65 535 байт эта ошибка стоит около 1168 нс на пакет
   и полностью съедает выигрыш от батчинга.
4. Частичная отправка батча — это потеря пакетов, а не фатальная ошибка.
   Считать её счётчиком (`Drops` в `outgoing.rs:90` уже есть) и продолжать.

**Критерий приёмки.** `cargo test --workspace` проходит; измеренный pps вырос;
регрессии в `cargo run --release --example packet_path -p mousevpn-data-plane`
нет (базовая линия 7069 Mbit/s, 1562 ns/packet).

## L3 — sleep-poll на паузе реконнекта

**Приоритет: низкий.**

`crates/linux-client/src/outgoing.rs:53`

```rust
while reconnect.paused.load(Ordering::Relaxed) && !stopping.load(Ordering::Relaxed) {
    std::thread::sleep(PAUSE_POLL);
}
```

`PAUSE_POLL = 5ms` — ровно тот шаблон, который убрали из Android. Урон здесь
ограничен: цикл работает только во время реконнекта, а не в установившемся
режиме. Но при выполнении L2 появится `poll`, и паузу естественно перевести на
то же событие пробуждения вместо сна.

Делать вместе с L2, отдельно не имеет смысла.

## L4 — Остановка ждёт следующего пакета

**Приоритет: низкий.**

`tun.receive` в `outgoing.rs:45` блокирующий (Linux-клиент не вызывает
`set_nonblocking`), поэтому `stopping` проверяется только после прихода пакета.
На тихом туннеле остановка подвисает. Закрывается автоматически при выполнении
L2, отдельной задачей не является.


Для задач, затрагивающих пакетный путь:

```sh

```

Базовая линия: 7069 Mbit/s, 1562 ns/packet на buffer-reusing пути. Замечание:
этот бенчмарк меряет только криптографический путь в изоляции и **не поймает**
регрессию в TUN-воркере или в работе с буферами. Для задач W4 и L2 нужен
end-to-end замер через реальный туннель (`iperf3` в обе стороны с фиксацией pps),
иначе изменение нельзя считать проверенным.

Windows-задачи требуют проверки на реальной Windows-машине: в CI и на Linux
собирается только заглушка (`platform_stub.rs`, `app_bypass_stub.rs`).
